## 2. Project Overview

**Project name:** Advanced Music Recommendation System

**Primary language:** Python

**Preferred application framework:** Streamlit

**Interface preference:** Minimal, clean, modern, easy to understand,
and not visually crowded.

selected song and musical preferences. The recommendations must be
generated by a real recommendation algorithm using the dataset, rather

## 3. Problem Statement

Music listeners may have difficulty discovering songs that match their
interests. The project aims to help users discover relevant music by
analyzing information about songs and comparing their characteristics.

A user should be able to select a song and optionally specify
preferences such as genre or artist. The system should process those
inputs and return a ranked list of similar or relevant songs, with an
understandable similarity score or explanation where practical.

## 5. Intended Recommendation Approach

### Primary approach

Use **Content-Based Filtering** as the main recommendation method.

The system should compare songs using the features that are actually
available in the selected dataset. Candidate features may include:

-   Genre
-   Artist
-   Track name or other text metadata, where useful
-   Danceability
-   Energy
-   Acousticness
-   Instrumentalness
-   Valence
-   Tempo
-   Loudness
-   Speechiness
-   Other relevant audio features present in the dataset

Do not assume every listed feature exists in the chosen dataset. Inspect
the real dataset schema first and document which fields are used or
excluded.

### Similarity method

Use **Cosine Similarity** as the initial similarity measure, with
suitable preprocessing and feature representation.

Potential preprocessing methods include:

-   Handling missing values
-   Removing or managing duplicate records
-   Encoding categorical or text features
-   Scaling numerical features
-   Combining feature groups in a justified way

The agent should choose and explain an appropriate implementation. For
example, numerical audio features may be scaled, while text or
categorical features may be encoded using a suitable vectorization
method. Avoid mixing feature types without a clear strategy.

### Personalization

Allow user preferences to influence ranking. Possible preferences
include:

-   A selected reference song
-   Preferred genres
-   Preferred artists
-   Optional controls for how strongly preferences affect results

The task plan should specify how these preferences will be represented
and combined with song similarity. Do not claim the system learns a
user's long-term listening behavior unless user history or feedback is
actually implemented.

### Scope boundary

The initial version should focus on content-based recommendations.
Collaborative filtering or a hybrid recommender may be considered as an
optional extension only if time, data, and assignment scope allow. Do
not make an advanced hybrid model a required feature unless its value
and implementation plan are justified.

## 7. Application Features

The initial application should include the following user-facing
features.

### 7.1 Home / Introduction

-   Show the project name and a short explanation.
-   Explain briefly how recommendations are generated.
-   Keep the layout simple and readable.

### 7.2 Song Selection

-   Let the user search for or select a song from the available dataset.
-   Display useful identifying information, such as track name and
    artist.
-   Handle cases where a song cannot be found.

### 7.3 Music Preferences

-   Allow the user to choose one or more preferred genres if genre data
    is available.
-   Allow optional artist preferences if artist data is available.
-   Make it clear which preferences are optional.

### 7.4 Recommendations

-   Generate a ranked list of approximately 5--10 recommendations.
-   Exclude the selected reference track from its own recommendation
    results.
-   Avoid returning duplicate recommendations.
-   Display available track information, such as song title, artist, and
    genre.
-   Show a similarity score in a way that is not misleading.
-   Make clear that a similarity score is an algorithmic score, not a
    guarantee that a user will like a song.

### 7.5 Model / About Section

-   Explain the content-based filtering approach.
-   Explain the role of preprocessing and cosine similarity.
-   Explain how user preferences affect ranking.
-   Describe important limitations.

### 7.6 Error Handling

Handle cases such as:

-   Empty or invalid input
-   Song not found
-   Missing dataset or unavailable data file
-   Missing values in relevant fields
-   No recommendations available after filtering
-   Unexpected application errors

## 10. Evaluation and Testing

The project must include evidence that the recommendation method works
as intended.

The agent should propose an evaluation plan appropriate for a
content-based recommender and the available dataset. Consider:

-   Unit or functional tests for preprocessing and recommendation
    functions
-   Tests using several different reference songs
-   Checks that the selected song is not recommended to itself
-   Checks for duplicate results and invalid scores
-   Checks that genre or artist filters behave correctly
-   Inspection of whether recommendations are musically or descriptively
    similar
-   A suitable quantitative evaluation method, if the dataset provides
    the information needed

Do not report precision, recall, accuracy, or other metrics unless they
are defined appropriately and actually calculated from suitable data. If
ground-truth user preferences or relevance labels are unavailable,
explain that limitation and use a defensible evaluation strategy rather
than inventing labels or results.

Include a discussion of limitations, such as dependence on dataset
features, limited understanding of user taste, popularity or catalog
bias if relevant, and the cold-start or diversity limitations of
content-based methods.
